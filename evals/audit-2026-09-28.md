# Concurrent-root transaction audit — September 28, 2026

Detector change: `batch-observable-writes` and `assign-observable-fields` report a review (`candidate`) instead of a
`change` when every React renderer in the file's workspace can only create concurrent roots. Analysis baseline:
`4a69db28eac4662bf1b99b2f97747a1e861a57cb`. No pin or target changed.

## Runtime evidence

`tests/runtime/concurrent-root-transactions.test.ts` (React 19.2.8, `@legendapp/state` 3.0.0-beta.48, jsdom) writes two
paths after a timer, outside `act`. Separate and batched writes produce the same render count and a single commit of the
final state, with and without StrictMode. Only a non-React `observe` that reads both paths records the intermediate
state, and a parent `onChange` listener fires once per write. `syncObservable` persistence queues changes until a
microtask, so it saves both writes together either way. Legacy roots do not coalesce writes made outside a React event,
so those findings stay changes.

## Follow-up: New Architecture app hosts

React Native 0.74 to 0.81 creates concurrent roots when the New Architecture is on, which only the app host decides. A
workspace with such a declaration now qualifies when it has at least one app host and every host enables the New
Architecture on each platform it builds. An app host is a package whose platform directory holds a build entry point
(`Podfile`, `settings.gradle`, or a Windows solution) or that has an Expo app config. Native module packages ship
platform sources without one, so they are not hosts. Explicit settings count, and so does Expo SDK 53 and 54's documented
default. A Podfile that compares `RCT_NEW_ARCH_ENABLED` instead of assigning it, or an app delegate that returns false
from `newArchEnabled`, keeps the host unproven.

legend-music compares the variable in its macOS Podfile, and legend-photos' macOS app delegate returns false, so both
stay legacy. Every pinned application has a zero delta. In the unpinned React Native macOS workspace, the shell's Podfile
assigns the variable and its Expo config enables the New Architecture. Its 33 transaction findings
(`assign-observable-fields` 19, `batch-observable-writes` 14) move from change to review.

## Follow-up: React DOM 18 client roots

React DOM 18 still exports `render` and `hydrate`, so its version alone cannot prove a concurrent root, but
`createRoot` and `hydrateRoot` from `react-dom/client` create one. A workspace with a React DOM 18 declaration now
qualifies when each package that declares it (outside a published peer range) creates a root through
`react-dom/client` in its own source, or runs under Next.js 13.1 or later. No analyzable source file anywhere in the
workspace may import a root API from `react-dom` or `react-dom/profiling`, call one on the `ReactDOM` UMD global,
re-export one, load either module through `require` or `import()`, or use a namespace import of either for anything
but a non-root member. A React DOM 18 package whose root the scan cannot find stays unproven, so framework-created
roots other than Next.js keep today's legacy verdict.

Next.js: `next@13.0.0`'s pages client chooses `require('react-dom/client')` or `require('react-dom')` from the
`__NEXT_REACT_ROOT` build flag and still calls `ReactDOM.render` and `ReactDOM.hydrate` on the second path. From
`next@13.1.0` (checked in 13.1, 13.2, 13.3, and 13.4 tarballs), `dist/client/index.js` requires only
`react-dom/client` and hydrates with `hydrateRoot`; the app router's `dist/client/app-index.js` uses `createRoot` and
`hydrateRoot` from 13.0.

### Runtime evidence

A jsdom probe mounts one component that subscribes to two paths, then writes both after a timer, outside `act` and
outside any React event. React 18.3.1, react-dom 18.3.1, jsdom 26.1.0:

| Root              | `@legendapp/state` (hook) | Separate writes: renders, commits | Batched writes: renders, commits |
| ----------------- | ------------------------- | --------------------------------- | -------------------------------- |
| `createRoot`      | beta.30 (`useSelector`)   | 1, `1/true`                       | 1, `1/true`                      |
| `hydrateRoot`     | beta.30 (`useSelector`)   | 1, `1/true`                       | 1, `1/true`                      |
| `ReactDOM.render` | beta.30 (`useSelector`)   | 2, `1/false` then `1/true`        | 1, `1/true`                      |
| `createRoot`      | beta.48 (`useValue`)      | 1, `1/true`                       | 1, `1/true`                      |
| `hydrateRoot`     | beta.48 (`useValue`)      | 1, `1/true`                       | 1, `1/true`                      |
| `ReactDOM.render` | beta.48 (`useValue`)      | 2, `1/false` then `1/true`        | 1, `1/true`                      |

React 18's client roots coalesce the writes exactly as React 19 does in `tests/runtime/concurrent-root-transactions.test.ts`;
only the legacy root renders the intermediate state. The repository pins React 19 for its runtime suite, so this
probe ran from a scratch install and is recorded here rather than in the suite.
